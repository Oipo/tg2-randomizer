● Short answer: 0x50A00, 0x50C00 and 0x50E00 are not tables and not relevant —
  drop temp_tracks2/3/4. They're addresses in the middle of the per-track
  path-data blob that the 0x50000 rows point into. Mapping all 64 header rows:
  the path blocks occupy file 0x50200–0x51988 contiguously, one block per track,
  and no row starts at $8A00/$8C00/$8E00 — those offsets fall inside the blocks
  of tracks 4, 54 and 23 respectively. So shuffling 8-byte chunks at those
  offsets would just scramble three random tracks' road geometry. (They likely
  caught your eye in hexdumps because the 4-byte bitfield path records have a
  regular, table-like look.)

  On the rest of the randomize_tracks block:

  - The shuffle logic itself is correct — draw-and-erase from the remaining pool
  produces a uniform permutation, and applying the same pos to all lists keeps
  them in lockstep. O(n²) erases are irrelevant at n=64.
  - Shuffling 0x50000 rows by value is safe: each row carries a pointer (word0)
  into bank $8A, and since you don't move the blocks themselves, no relocation
  is needed. The old commented experiment that moved blocks around was solving a
  problem that doesn't exist.
  - But it's incomplete, and that's the actual minimap bug: your experiment just
  proved the minimap (and scenery) live in the bank $87 graphics records. A
  0x50000-only shuffle moves geometry+weather while every slot keeps its
  original minimap/scenery — exactly the mismatch you've been hunting. The same
  permutation must also be applied to the 64 contiguous record-pointer words at
  0x3A676 (2 bytes each, all records in the same bank so plain word swaps are
  safe), and optionally the 64 music bytes at 0x0FA20C.

  So the corrected core would be:

  if(randomize_tracks) {
      vector<uint32_t> perm(64);
      iota(perm.begin(), perm.end(), 0);
      shuffle(perm.begin(), perm.end(), rng);

      constexpr PC_addr path_table = 0x50000;        // 8-byte rows: path
  offset, length, weather
      constexpr PC_addr gfx_record_table = 0x3A676;  // 16-bit record offsets in
  bank $87 (scenery + minimap)
      constexpr PC_addr music_table = 0x0FA20C;      // 1 byte per track

      vector<char> orig(bytes);
      for(uint32_t slot = 0; slot < 64; slot++) {
          uint32_t src = perm[slot];
          copy_n(orig.begin() + path_table + src*8, 8, bytes.begin() +
  path_table + slot*8);
          copy_n(orig.begin() + gfx_record_table + src*2, 2, bytes.begin() +
  gfx_record_table + slot*2);
          bytes[music_table + slot] = orig[music_table + src];
      }
  }

  (needs #include <numeric> for iota). Two smaller things while you're in there:
  line 253 (randomize_tracks = false;) unconditionally overrides the -t flag —
  fine as a temporary disable, just don't forget it; and remember to comment out

  Where the upgrades live. The shop's authoritative state is a 0x11C-byte block

  every byte through ROM tables into $06xx per-player parameters:

  - Acceleration: engine level indexes $80:D036/D03A (28 2C 30 34 / 68 6C 70 74)

  6 entries but with taller ratios (that's your no-new-gear upgrade), level 3
  adds the 6th. Ratios are used as the divisor in $4206 hardware division at
  $80:ECED.

  rain/snow rows are visibly slipperier).

  is front/side/rear isn't pinned yet.
  - Nitro: 6 charges always ($80:D0C2), DEC $01A6 on use with a fixed 0x230-tick

● That behaviour matches the code exactly. The push isn't a continuous cornering
  model — it's per road segment. The race engine streams the track's 4-byte
  path records (bank $8A) into the ring buffer at $7E:9000+, and each frame the
  physics looks at the curvature field of the segment currently under your car
  (LDA $7E9010,X). The push only fires when that segment's curvature field is
  set in the relevant direction (the BMI/BPL guards), and its strength is
  curvature × speed × grip.

  So what you felt is the track data, not the physics being inconsistent:

  - "Only some corners" — gentle corners are authored with small (or zero)
  curvature values in their path records, so the product is too small to feel,
  especially below top speed.
  - "Only parts of some corners" — a corner is built from several consecutive
  path records, and typically only the sharper mid-corner segments carry big
  curvature values. As you cross from a marked segment to an unmarked one, the
  force switches on and off — hence the "sudden" shove rather than a smooth
  pull.
  - Straights — curvature is zero or the sign guard skips the whole block, so
  grip is irrelevant there, which is why steering feel doesn't change.

  One implication if you ever randomize or tune grip: its effect is
  multiplicative with each track's authored curvature, so a global grip change
  will be dramatic on tracks with sharp-segment-heavy corners and nearly
  invisible on flowing ones. The per-corner sharpness itself lives in the path
  records at 0x50200+ (the bitfields the road builder extracts), not in the grip
  grid.

● It's not a per-car setting — no upgrade touches it. Straight-line steering
  speed is built from shared curve tables plus two hardcoded constants, all now
  verified. The pipeline:

  1. Ramp: while you hold left/right, the "wheel" accumulator (dp $1C/$1D)
  charges by C633_curve[(wheel+speed)>>5] × BE13[gear] × frame_delta. The curve
  at $80:C633 starts flat at E258.
  2. Scale: lateral velocity $10 = wheel × BDFB[current gear] — note this is the
  same byte that serves as the gear ratio, so steering scale grows with gear (≈
  speed-proportional turning).
  3. Final boost: $10 += $10 × #$70/256 (≈ ×1.44) — a hardcoded constant.
  4. Centering: the wheel is pulled back by a force from curve $80:C833 (grows
  with lateral speed), plus a #$0200 bonus while holding one of the configured
  buttons (a brake-steer effect); crossing center snaps the wheel to 0.
  5. High-speed nerf: above RPM-index 0xE0, negative corrections from $80:CA33
  (FF6E, FEDC...) reduce response.

  Here's the full opponent model:

  Car array: 20 records of 0x40 bytes at $7E:C400. Slot 0 = P1, slot 1 = P2
  (their handlers E6C4/E6DE just add the real player speed $0212/$024E to their

  Drone speed (handler $80:E424 → cruise $80:E541): each drone accelerates by
  its +0x30 parameter until its speed word hits the +0x32 cap, then holds. Both
  are assigned once at race init ($80:D2B1-D2C2):

  nearly twice as fast.

  and others it feels slightly more catchable.

  0x60 road units of either player → enable full lateral simulation with lane

  faster than your car until you've bought enough upgrades.
